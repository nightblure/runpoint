# Roadmap поддержки Go

## Цель

Расширить `runpoint` поддержкой Go, сохранив главное свойство проекта: конфигурация и запуск не зависят от конкретной IDE. CLI остаётся источником параметров запуска, а Zed, PyCharm и другие IDE используются только как клиенты отладки.

Этот документ описывает возможное развитие проекта. Он не является утверждённым планом реализации.

## Конфигурация

Добавить тип runtime, сохранив Python значением по умолчанию для совместимости с существующими конфигурациями:

```json
{
  "alias": "go-tests",
  "runtime": "go",
  "command": "test ./...",
  "cwd": "apps/service",
  "load_env_file": false
}
```

Предполагаемые runtime:

- `python` — существующее поведение;
- `go` — команды Go toolchain.

Поддержку произвольных исполняемых файлов и других языков не следует добавлять заранее.

## Границы слоёв

Текущее разделение проекта подходит для расширения:

- `domain` — тип runtime и правила допустимых команд для Python и Go;
- `data` — чтение `runtime` из конфигурации и применение значения `python` по умолчанию;
- `services` — поиск инструментов, построение команд, окружение и runtime-специфичные операции;
- `use_cases` — единый сценарий подготовки и запуска entrypoint;
- `cli` — общие параметры запуска, выбор entrypoint и пользовательский вывод.

Runtime-абстракции следует вводить только вместе с первой реализацией Go, когда появятся как минимум две реальные стратегии. Предпочтительна небольшая стратегия или явная диспетчеризация без контейнера зависимостей и иерархии базовых классов.

## Запуск без отладки

Первый этап должен поддерживать стандартные команды:

- `go test ./...`;
- `go run ./cmd/api`;
- `go build ./cmd/api`.

Основные правила:

- `go` находится через `PATH` либо через явно определённый в будущем путь;
- команда запускается напрямую без shell;
- `go test` распознаётся как тестовая точка входа;
- тестовые точки не читают `.env`;
- переменные из `os.environ` и явного `entrypoint.env` остаются доступны;
- `cwd`, дополнительные аргументы и замена текущего процесса сохраняют существующую семантику.

Поддержку запуска заранее собранного бинарного файла следует рассматривать отдельно: это уже общий executable runtime, а не команда Go toolchain.

## Отладка

Для Go потребуется Delve. Его модель отличается от `debugpy`:

- `debugpy` может сам запустить Python target и ждать подключения IDE;
- `dlv dap` поднимает DAP-сервер, но параметры запуска программы обычно получает от IDE в DAP-запросе;
- headless-режимы Delve могут использовать собственный RPC-протокол, поддержка которого различается между IDE.

До реализации нужно провести отдельный технический эксперимент:

1. Запустить `dlv dap` из CLI с фиксированными `cwd`, портом и окружением.
2. Подключить Zed и проверить запуск либо attach без дублирования project-конфигурации.
3. Повторить тот же сценарий в PyCharm.
4. Сравнить поддерживаемые DAP-запросы, передачу аргументов, окружения и рабочей директории.
5. Выбрать только общий для обеих IDE сценарий.

Если обе IDE поддерживают одинаковое подключение, пользовательский сценарий должен выглядеть так:

```shell
runpoint go-api --debug --debug-port 5679
```

После этого IDE подключается к DAP-порту и не определяет параметры приложения самостоятельно.

Нельзя обещать полную IDE-независимость Go-отладки до проверки совместимости Delve DAP с Zed и PyCharm.

## Этапы

### 1. Домен и конфигурация

- Добавить runtime `python` и `go`.
- Сохранить `python` значением по умолчанию.
- Добавить валидацию команд Go.
- Зафиксировать обратную совместимость существующих конфигураций тестами.

### 2. Go toolchain

- Реализовать поиск `go`.
- Добавить построение команд `test`, `run` и `build`.
- Сохранить запуск без shell.
- Покрыть обработку `cwd`, target-аргументов и отсутствующего executable.

### 3. Окружение тестов

- Распознавать `go test` как тестовый entrypoint.
- Не читать существующий или отсутствующий `.env` для тестов.
- Сохранять process env и явный `entrypoint.env`.
- Переиспользовать существующие гарантии Python-тестов.

### 4. Delve spike

- Проверить DAP-сценарий в Zed.
- Проверить тот же сценарий в PyCharm.
- Зафиксировать общую модель launch/attach.
- Определить семантику `--no-debug-wait` и Python-специфичного `--debug-subprocesses` для Go.

### 5. Go debug

- Добавлять только после успешного Delve spike.
- Запускать Delve как отдельную runtime-стратегию.
- Сохранить единые CLI-флаги там, где их семантика действительно совпадает.
- Явно отклонять неподдерживаемые опции вместо их молчаливого игнорирования.

## Критерии готовности

- Существующие Python-конфигурации работают без изменений.
- Go run/test/build не требуют конфигурации IDE.
- Python- и Go-команды запускаются без shell.
- Правила загрузки окружения одинаково проверены для обоих runtime.
- Go-отладка подтверждена вручную в Zed и PyCharm.
- IDE не дублирует `cwd`, аргументы приложения и переменные окружения, если выбранный DAP-сценарий позволяет передать их со стороны CLI.
- Все тесты, линтеры и сборка проходят.

## Открытые вопросы

- Поддерживают ли Zed и PyCharm один и тот же внешний сценарий `dlv dap`?
- Может ли CLI полностью определить target, аргументы и окружение, или часть launch-конфигурации неизбежно останется в IDE?
- Нужен ли на практике явно настраиваемый путь к `go` и `dlv`?
- Следует ли поддерживать запуск готовых Go-бинарников отдельным runtime?
- Нужно ли в будущем переименовывать `runpoint`, если Go станет полноценным runtime?
